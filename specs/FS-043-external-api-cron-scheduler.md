# FS-043: External API & Cron Scheduler

## Overview

The External API & Cron Scheduler specification defines the system's machine-to-machine
HTTP interface and its scheduled-maintenance subsystem. It covers four cooperating concerns:

1. **API key management** — administrators register API keys, each bound to a single source
   IP address, with per-key permission flags (create tickets / execute cron) and an
   active/disabled status. Keys are auto-generated, immutable secrets.
2. **The HTTP API dispatcher** — a lightweight, lazily-loadable, nestable URL router that maps
   incoming request method + path to a controller method. The router is method-agnostic (it has
   generic GET/POST/DELETE matcher helpers) but the only mounted routes are POST ticket creation and
   a nested POST remote-cron route.
3. **The external ticket-create API endpoint** — a stateless POST endpoint accepting ticket
   payloads in three interchangeable wire formats (XML, JSON, Email), authenticated by API key,
   validated against a fixed field allow-list, with attachment intake and standard HTTP status
   responses.
4. **The cron scheduler** — a fixed inventory of background maintenance jobs (mail fetch,
   ticket-overdue sweep, expired-lock cleanup, system-log purge, orphaned-file cleanup) that can
   be invoked three ways: a command-line local cron call, a remote HTTP cron call (API-key
   protected), and an "autocron" web fallback triggered by staff page loads.

This specification owns the API key entity and its admin management screens, the URL dispatcher
routing mechanics, the API request authentication/parsing/validation pipeline, the ticket-create
controller's accepted fields and response codes, the cron job inventory and each job's exact
trigger conditions and cadence, and the autocron fallback mechanics. It does **not** own: the
ticket-creation business logic itself (referenced — owned by FS-011/FS-021), the email-sourced
parse-to-ticket threading path (referenced — owned by FS-041), the AJAX handler bodies
(referenced — the shared `AjaxController` base class is documented here as shared infrastructure;
individual handlers belong to their domain specs), the mail-fetch IMAP/POP3 mechanics (referenced
— owned by FS-041), and enum/table-schema definitions (canonically owned by FS-091).

**Stateless API note**: The API realm explicitly disables sessions. The session save handler is
overridden to no-ops and the constant `DISABLE_SESSION` is set, so API requests do not create or
consume session database records.

## Functional Requirements

### FS-043.1: API Key Entity & Auto-Generated Secret

**Description**: The system shall maintain a registry of API keys, each a self-contained record
bound to a source IP address, carrying an auto-generated secret, permission flags, an active
status, and free-text admin notes.

**Acceptance Criteria**:
- Each API key record has the persisted attributes: `id`, `apikey` (the secret), `ipaddr`
  (bound source IP), `isactive` (active/disabled), `can_create_tickets`, `can_exec_cron`,
  `notes`, `created`, `updated`. (Canonical schema → FS-091, table `ost_api_key`.)
- The `apikey` secret is **auto-generated by the system** on key creation and is never
  user-supplied: it is the uppercased MD5 hash of `time() + ipaddr + MD5(random 16-char code)`,
  yielding a 32-character uppercase hexadecimal string.
- The secret is **immutable**: there is no edit path for the key value or the bound IP. To change
  either, the admin must delete the key and add a new one (the admin UI states *"API Key is
  auto-generated. Delete and re-add to change the key."*).
- On creation the bound `ipaddr` is **required** and must pass IP-address validation; an invalid
  or missing IP yields the field error *"Valid IP required"* and the key is not created.
- Editing an existing key updates only `isactive`, `can_create_tickets`, `can_exec_cron`, and
  `notes` (plus the `updated` timestamp); `ipaddr` and `apikey` are left untouched.
- `created` is set once at insert; `updated` is refreshed on every save (insert or update).

### FS-043.2: API Key Administration Screens

**Description**: The system shall provide administrator-only screens to list, add, edit,
enable/disable, and delete API keys.

**Acceptance Criteria**:
- The API keys screens are reachable from the staff control panel under the **Manage** tab and
  require an authenticated staff member with the **admin** flag. Access is gated at **two** layers:
  (1) the controller script bootstraps through the **admin** include, which enforces the admin
  control-panel access gate (→ FS-002) at the entry point; and (2) each view template additionally
  `die('Access Denied')` if the admin-context constant (`OSTADMININC`) is not defined or
  `$thisstaff` is absent / not an admin.
- An `id` request parameter that does not resolve to a known key surfaces the error *"Unknown or
  invalid API key ID."* and the screen continues without a loaded key.
- **List view** (`apikeys.inc.php`): a paginated, sortable table of all keys showing the key
  value (linked to its edit page), bound IP, status (`Active` / `Disabled`), date added, and last
  updated. Page size is the system `PAGE_LIMIT`.
- List sortable columns: by key (`apikey`), status (`isactive`), IP (`ipaddr`), date added
  (`created`), last updated (`updated`); default sort is by key, descending.
- **Add view** (`apikey.inc.php`, `a=add`): a form collecting the required bound **IP Address**,
  the **Status** radio (Active default / Disabled), the two service checkboxes **Can Create
  Tickets (XML/JSON/EMAIL)** and **Can Execute Cron**, and **Admin Notes**. On success: *"API key
  added successfully"*.
- **Edit view** (`apikey.inc.php`, with `id`): the same form but the IP Address and API Key are
  shown read-only; only Status, the two service checkboxes, and Notes are editable. On success:
  *"API key updated successfully"*.
- **Bulk actions** (mass-process on the list): **Enable**, **Disable**, **Delete** the checked
  keys. At least one key must be selected else *"You must select at least one API key"*. Partial
  success reports *"N of M selected API keys [enabled|disabled|deleted]"*; full success reports
  the all-succeeded message. Delete is irreversible and warns *"Deleted keys CANNOT be
  recovered."* with a confirmation dialog.
- **Bulk action mechanics**: Enable / Disable perform a single bulk status update over the selected
  ids and compare the affected-row count against the selection count to decide full-vs-partial
  messaging; Delete iterates the selected ids, loading and deleting each key individually and
  counting successes. An unrecognized mass-process action yields *"Unknown action - get technical
  help"*; an unrecognized top-level command yields *"Unknown action/command"*.
- All POST submissions are CSRF-protected (a CSRF token is embedded in every form).

### FS-043.3: HTTP API URL Dispatcher

**Description**: The system shall route inbound HTTP API requests by matching the request's HTTP
method and path against an ordered table of URL patterns, invoking the first matching controller
method.

**Acceptance Criteria**:
- The dispatcher resolves the request **path info** (`PATH_INFO`, falling back to
  `ORIG_PATH_INFO`) against an ordered list of pattern matchers; the first match wins.
- Each matcher carries a regular-expression path pattern, an optional required HTTP method, a
  target controller class + method (expressed as `file:Class` so the class file is lazily
  included on dispatch), and any static arguments. Named regex capture groups become positional
  arguments to the target method.
- Patterns may nest: a matcher may point at a sub-dispatcher (sub-pattern group), in which case
  the matched prefix is stripped and the remainder is resolved against the sub-dispatcher, with
  already-captured arguments carried forward.
- The mounted route table is exactly:

  | Method | Path pattern | Target | FR |
  |--------|--------------|--------|-----|
  | POST | `^/tickets\.(xml\|json\|email)$` | ticket-create controller `create($format)` | FS-043.4 |
  | POST | `^/tasks/` + sub-pattern `^cron$` | cron controller `execute()` | FS-043.7 |

  (The matched `format` capture — `xml`, `json`, or `email` — is passed as the create method's
  argument. No GET, PUT, or DELETE API routes are mounted; ticket modification and deletion are
  not exposed.)
- The cron route is **not** a flat pattern but a **nested sub-dispatcher**: the top-level matcher
  `^/tasks/` points at a child dispatcher carrying the single sub-pattern `^cron$`. On a match the
  `/tasks/` prefix is stripped and `cron` is resolved against the child, demonstrating the
  prefix-strip / arg-carry-forward nesting mechanic above. The effective full path is therefore
  `/tasks/cron`.
- The dispatcher framework defines **generic method-typed matcher helpers** for `GET`, `POST`, and
  `DELETE` (and an untyped/any-method matcher). Although only POST routes are mounted in 1.7, the
  routing layer is method-agnostic and could mount GET/DELETE matchers; the *absence* of any
  GET/PUT/DELETE entry in the table above — not a dispatcher limitation — is what makes the API
  creation-only.
- The dispatcher is **lazy-loadable**: a route file may be referenced by path and only `include`d
  the first time the dispatcher is resolved (the URL list is loaded on first access, then the file
  reference is cleared so it loads at most once).
- **Method emulation**: if a `_method` GET query argument is present, its uppercased value
  overrides the request method before matching (so a client unable to send a raw POST may emulate
  one via `?_method=POST`).
- If a matcher's method requirement does not equal the request method, that matcher does not
  match (and resolution continues to the next).
- If no pattern matches the resolved path, the system responds **HTTP 400 "URL not supported"**.
- If a matched target is found but is not callable, the system responds **HTTP 500 "Dispatcher
  compile error. Function not callable"**.

### FS-043.4: External Ticket-Create API Endpoint

**Description**: The system shall accept new-ticket submissions via HTTP POST to
`/api/tickets.<format>`, authenticated by API key, parsing the request body according to the
URL-declared format, validating it against a fixed field allow-list, and creating a ticket.

**Acceptance Criteria**:
- The endpoint accepts three formats determined by the URL extension: **xml** → `tickets.xml`,
  **json** → `tickets.json`, **email** → `tickets.email`.
- The endpoint requires a valid API key (FS-043.6) **with the `can_create_tickets` permission**;
  absent or unauthorized → **HTTP 401 "API key not authorized"**.
- The request body is read from the raw input stream (standard input when invoked via CLI;
  otherwise the raw HTTP request body). If that input stream cannot be opened, the endpoint
  responds **HTTP 400 "Unable to read request body"**.
- The body is parsed by the format-specific parser:
  - **xml**: parsed as XML; requires the XML parsing capability, else **HTTP 501 "XML extension
    not supported"**. A `<ticket>` root wrapper is unwrapped. A `phone` element's `ext` attribute
    becomes `phone_ext`; `alert` and `autorespond` are coerced to boolean; attachment file bodies
    are mapped to a `data` field.
  - **json**: parsed as JSON. A `phone` value may embed an extension after a capital `X`
    (e.g. `3185558634X123` → number + `phone_ext`); `alert`/`autorespond` coerced to boolean;
    attachments are supplied as RFC-2397 data-URL strings keyed by filename, with optional MIME
    type, optional `base64` encoding hint, and optional `charset` (non-UTF-8 charsets are
    converted to UTF-8 for storage). A bare (non-`data:`) string is treated as plain text.
  - **email**: parsed as a raw RFC-822 email message (see FS-043.5 and FS-041). After parsing, the
    email parser applies **default fill-in** and reply-detection via the shared pipeline (wire
    framing → FS-043.14; fixup defaults → FS-041.5.3; threading precedence → FS-041.6).
- An unsupported/unrecognized format string yields **HTTP 415 "Unsupported data format"**.
- A body that fails to parse yields **HTTP 400** with the parser's last-error message; for the
  ticket endpoint a structure-validation failure yields **HTTP 400 "Unexpected or invalid data
  received"**.
- **Accepted top-level fields** (anything else is rejected as unexpected data): `alert`,
  `autorespond`, `source`, `topicId`, `name`, `email`, `subject`, `phone`, `phone_ext`,
  `attachments`, `message`, `ip`, `priorityId`. Each `attachments` entry accepts only `name`,
  `type`, `data`, `encoding`.
- For the **email** format, the accepted-field set is additionally extended with: `header`,
  `mid`, `emailId`, `ticketId`, `reply-to`, `reply-to-name`, `in-reply-to`, `references`.
- Any field key not in the allow-list for the chosen format yields **HTTP 400 "<path>: Unexpected
  data received"** (the path includes the offending key).
- On successful creation: **HTTP 201**, with the response body being the new ticket's **external
  ticket ID** (its public ticket number).
- **Format branching in the controller**: for the **xml** and **json** formats the controller reads
  and parses the body, then calls the ticket-create helper (FS-043.4 / FS-011). For the **email**
  format it instead runs the **email reply-detection branch** (FS-043.14) before falling back to
  creating a new ticket.
- If the create helper returns no ticket for an otherwise-error-free request, the endpoint responds
  **HTTP 500 "Unable to create new ticket: unknown error"**. If ticket creation accumulated
  validation errors, the endpoint responds **HTTP 400 "Unable to create new ticket: validation
  errors:"** followed by the flattened `key: value` error list (the filter-denied 403 case is
  handled per EC-439).

### FS-043.14: Email-Format Reply Detection & Default Fill-In

**Description**: When a ticket-create request arrives in the **email** format, the system dispatches
it through the shared parse / fixup / reply-detection / threading pipeline before creating a new
ticket. This FR owns only the **HTTP wire framing** of that path; the payload fixup defaults and the
reply-detection / threading precedence themselves are owned by FS-041.

**Acceptance Criteria**:
- The email-payload **fixup defaults** (force `source = "Email"`; `message`/`subject`/`emailId`
  fallbacks; strip `priorityId` when email-sourced priority is disabled) are owned by **FS-041.5.3**;
  the **reply-detection / threading precedence** (explicit `ticketId` → email-header match
  `in-reply-to`/`references`/`mid` → new-ticket fallback) is owned by **FS-041.6**. The controller
  invokes these and does not restate their logic.
- **HTTP wire framing (this spec):** the URL extension `tickets.email` dispatches to the email-format
  branch; the email accepted-field allow-list extension (FS-043.4) applies; and the single response
  for all reply / new-ticket outcomes is **HTTP 201** with the resulting ticket's external ID.

### FS-043.15: Local Email-Pipe Response Mapping (Reference)

**Description**: The system shall provide a local email-pipe controller variant that reuses the
ticket-create / reply-detection pipeline but maps outcomes to process exit codes for a mail-transfer
agent rather than HTTP statuses. (Inbound-pipe mechanics canonically owned by FS-041; only the
API-level response mapping is documented here because it specializes the API controller.)

**Acceptance Criteria**:
- The pipe controller extends the ticket API controller and **requires no API key** (it is gated by
  local server/MTA invocation, like local cron).
- It runs the email reply-detection branch (FS-043.14); on success it responds with the ticket
  **number** and a success exit code; if no ticket results it reports **HTTP 416 "Request failed -
  retry again!"**.
- Its response method translates HTTP codes to MTA process exit codes. The HTTP→exit-code mapping
  table (201→0 / 400→66 / 401-403→77 / 415-417/501→65 / 503→69 / 500→75) is canonically owned by
  **FS-041 BS-041.2** (parse/pipe mechanics); only the fact that this controller *specializes the
  API controller* to apply that mapping is documented here.

### FS-043.5: API Attachment Intake & Validation

**Description**: The system shall accept file attachments embedded in ticket-create API requests,
subject to a global enable flag, per-file type allow-listing, base64 decoding, and a maximum file
size, applying soft per-attachment validation.

**Acceptance Criteria**:
- If API attachments are globally disabled (config flag — shared with email attachments), the
  entire `attachments` collection is **discarded silently** before ticket creation.
- For each attachment, type/extension allow-listing is applied; a disallowed type sets a
  per-attachment error *"Invalid file type (ext) for &lt;name&gt;"* but does **not** abort the
  whole request (soft fail — the ticket is still created without that file).
- If an attachment declares `encoding = base64`, the data is base64-decoded; malformed base64
  sets the per-attachment error *"&lt;name&gt;: Poorly encoded base64 data"*.
- If a maximum file size is configured and an attachment's size (declared `size` or decoded
  length) exceeds it, the per-attachment error reads *"File &lt;name&gt; (&lt;actual&gt;) is too
  big. Maximum of &lt;max&gt; allowed"* (sizes human-formatted).
- Multiple files may share the same filename (allowed).
- Per-attachment errors are recorded on the attachment, not raised as request-level failures; the
  request continues to ticket creation.

### FS-043.6: API Key Authentication & IP Binding

**Description**: The system shall authenticate every protected API request by an `X-API-Key`
request header whose value matches a registered, active key, and whose source IP equals the key's
bound IP.

**Acceptance Criteria**:
- The API key is read from the **`X-API-Key`** HTTP request header.
- The key lookup is **only attempted when both** the `X-API-Key` header **and** a source IP
  (`REMOTE_ADDR`) are present; if either is absent no lookup runs and authentication fails with
  "Valid API key required". The resolved key object is **cached on the controller** for the life of
  the request (looked up at most once).
- The key is looked up by secret value **and** by source IP (`REMOTE_ADDR`); a key matches only
  when both the secret and the IP correspond to a registered record. (Because the lookup query
  itself filters on IP, the subsequent active/IP re-check in the authentication path primarily adds
  the disabled-key rejection.)
- If no key is supplied / not found → **HTTP 401 "Valid API key required"**.
- If the key is found but is **disabled** (`isactive` false) **or** the request source IP does not
  equal the key's bound `ipaddr` → **HTTP 401 "API key not found/active or source IP not
  authorized"**.
- A successfully authenticated key is then additionally checked for the **specific permission** the
  endpoint requires (`can_create_tickets` for ticket creation, `can_exec_cron` for cron); lacking
  the permission → **HTTP 401 "API key not authorized"**.
- The effective source IP honors a reverse-proxy `X-Forwarded-For` header (left-most value),
  rewritten into `REMOTE_ADDR` at request bootstrap (mechanism owned by FS-001); IP binding is
  evaluated against that rewritten value.

### FS-043.7: Cron Job Inventory

**Description**: The system shall run a fixed set of background maintenance jobs when a full cron
cycle is invoked, executing them in a defined order and only when the system is not pending an
upgrade.

**Acceptance Criteria**:
- A full cron cycle (`Cron::run`) executes, in order: **(1) Mail fetch**, **(2) Ticket monitor**
  (overdue sweep + expired-lock cleanup), **(3) Purge logs**, **(4) Clean orphaned files**.
- A full cron cycle does **nothing** (returns immediately) if the core system object is
  unavailable **or** an upgrade is pending (schema signature mismatch).
- **Mail fetch** polls each active mail account whose configured fetch frequency has elapsed,
  pulling new messages into tickets. (Cadence and mechanics → FS-043.8 / FS-041.)
- **Ticket monitor** runs two sub-jobs:
  - **Overdue sweep**: flags up to **50** open, not-yet-overdue tickets per invocation as
    overdue; a ticket qualifies when, per its active SLA grace period or its explicit due date,
    it has aged past the threshold (see BS-432). Each newly overdue ticket logs the activity
    *"Ticket Marked Overdue"* / *"Ticket flagged as overdue by the system."*.
  - **Expired-lock cleanup**: deletes all ticket locks whose expiry is in the past, then
    optimizes the lock table.
- **Purge logs**: deletes system-log entries older than the configured log grace period (in
  months); if no grace period is configured (or non-numeric), the purge is a no-op.
- **Clean orphaned files**: deletes file records (of file-type "ticket") no longer referenced by
  any ticket, canned-response, or FAQ attachment, then deletes the corresponding orphaned file
  chunks. (Content-addressed file storage mechanics → FS-022.)

### FS-043.8: Mail-Fetch as Cron Job #1

**Description**: The cron scheduler runs mail-fetch as **job #1** of the full cron cycle (FS-043.7).
The fetch eligibility cadence, error-backoff policy, time-box, and per-account intake caps are owned
by FS-041; this FR records only the cron-side invocation.

**Acceptance Criteria**:
- The full cron cycle invokes **mail-fetch first**, before the ticket-monitor, purge-logs, and
  clean-orphaned-files jobs (ordering per FS-043.7 / BS-433).
- Mail fetch is skipped entirely when the global *email polling* setting is disabled.
- The per-account eligibility cadence, error-backoff (consecutive-error threshold and timeout
  window), the *"Mail Fetch Failure Alert"* admin alert, the per-cycle execution time-box, and the
  per-account `max_fetch` intake cap are all owned by **FS-041** (.3 / BS-041.5/6/15). This spec does
  not restate those numbers.

### FS-043.9: Remote HTTP Cron Execution

**Description**: The system shall allow a full cron cycle to be triggered remotely by an
authenticated HTTP POST.

**Acceptance Criteria**:
- The route is **POST `/api/tasks/cron`**.
- It requires a valid, active, IP-bound API key (FS-043.6) **with the `can_exec_cron`
  permission**; otherwise **HTTP 401 "API key not authorized"**.
- On authorization it runs a full cron cycle (FS-043.7), logs a debug entry *"Cron Job" / "Cron
  job executed [<source IP>]"*, and responds **HTTP 200 "Completed"**.
- A reference remote-call client is provided (`scripts/rcron.php`): it POSTs an empty body with
  the `X-API-Key` header and treats an HTTP 200 status as success (exit 0), else echoes the
  response and exits 1.

### FS-043.10: Local (Command-Line) Cron Execution

**Description**: The system shall allow a full cron cycle to be triggered from the command line
without an API key.

**Acceptance Criteria**:
- The local cron entry point runs only under a command-line invocation; if not run from the CLI it
  exits with the message *"cron.php only supports local cron calls - use http -> api/tasks/cron"*.
- CLI detection succeeds when the runtime SAPI begins with `cli`, or when neither a request method
  nor an HTTP host is present (CGI-via-CLI fallback).
- Local cron runs a full cron cycle (FS-043.7); **no API key is required** because access is
  implicitly gated by command-line/server access.
- The local responder uses process exit codes rather than HTTP: success exits **0** silently; on
  error it echoes the error text and exits **1**.
- Local cron reads any request body from standard input (consistent with the CLI input source in
  FS-043.4).

### FS-043.11: Autocron Web Fallback

**Description**: The system shall provide a fallback cron mechanism triggered by staff control-panel
page loads, so that time-sensitive maintenance still runs on installations without a configured
system cron.

**Acceptance Criteria**:
- Every staff control-panel page footer embeds a 1×1 transparent GIF request to `autocron.php`;
  loading it invokes the autocron handler. (The footer comment warns the image must not be
  removed or autocron ceases to function.)
- The autocron handler requires an authenticated staff session (it includes the staff bootstrap),
  emits the tiny GIF immediately, flushes/finishes the HTTP response, then performs the cron work
  in the background (it sets `ignore_user_abort` and removes the time limit).
- **Throttle**: autocron does real work at most **once every 180 seconds (3 minutes) per staff
  session**, tracked by `lastcroncall` on the session; loads inside that window are no-ops.
- Autocron also requires that the system is **not pending an upgrade**; if an upgrade is pending it
  does nothing.
- When it runs, autocron **always** executes the **Ticket monitor** job (overdue sweep + expired-
  lock cleanup) regardless of cron/mail settings.
- Autocron executes the **Mail fetch** job **only if** the *autocron enabled* setting is on; when
  it does, it logs a debug entry *"Auto Cron" / "Mail fetcher cron call [<staff username>]"*.
- Before running cron work, autocron clears the current-staff object so that any internal notes or
  auto-assignments produced by cron actions are not falsely credited to the triggering staff
  member.
- Autocron does **not** run the Purge-logs or Clean-orphaned-files jobs (those run only on a full
  cron cycle).

### FS-043.12: API Error Logging & Response Pipeline

**Description**: The system shall return a uniform error response for every API failure and record
it to the system log, including the offending API key when available.

**Acceptance Criteria**:
- Every API error emits an HTTP status + plain message via a common error path (`exerr`), which
  then **logs a warning** titled *"API Error (&lt;code&gt;)"* with the message body; the supplied
  `X-API-Key` value is appended to the logged message when present.
- Array-valued error details are flattened to a `key: value`-per-line string before responding.
- The default API response writes the status line and content with `Content-Type` defaulting to
  `text/html; charset=UTF-8`, a `Content-Length`, `Connection: Close`, and then terminates the
  request.
- The HTTP status verbose strings the system can emit include: `200 OK`, `201 Created`,
  `204 NoContent`, `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`,
  `405 Method Not Allowed`, `416 Requested Range Not Satisfiable`; any other code defaults to
  `500 Internal Server Error`.

### FS-043.13: Shared AJAX Controller Base (Infrastructure)

**Description**: The system shall provide a shared AJAX controller base, extending the API
controller, used by the in-application AJAX handlers; this FR documents only the shared base, not
the individual handlers.

**Acceptance Criteria**:
- The AJAX base extends the API controller and adds: a `staffOnly()` guard that responds **HTTP
  401 "Access Denied. IP &lt;source IP&gt;"** when there is no valid current staff member; a
  JSON-encoding helper (`json_encode`/`encode`); and a `get(var, default)` reader for GET
  parameters.
- The AJAX base does **not** require an API key (it is gated by the in-app staff/client session,
  not by the API-key pipeline).
- Concrete AJAX handler routing and behavior are owned by their respective domain specs (tickets,
  users, reports, config, content, etc.); this spec documents only the shared base class.

## Business Rules

### BS-430: API Keys Are IP-Bound, Single-Permission-Gated Secrets
**Rule**: An API request is authorized only when all of: a registered `X-API-Key` secret matches,
the key is active, the request source IP equals the key's bound IP, **and** the key carries the
specific permission flag the endpoint requires (`can_create_tickets` or `can_exec_cron`).
**Rationale**: Defense in depth — possession of the secret alone is insufficient; the call must
originate from the pre-registered host and the key must be explicitly entitled to the action.
**Examples**:
- A valid `can_create_tickets` key calling `/api/tasks/cron` → 401 (wrong permission).
- A valid key sent from an IP other than its bound IP → 401 (source IP not authorized).
- A disabled key → 401 even if secret + IP match.

### BS-431: API Key Secret Is System-Generated and Immutable
**Rule**: The API key secret is auto-generated (32-char uppercase hex MD5 of time + IP + random
seed) and the bound IP and secret cannot be edited; changing either requires deleting and
re-creating the key.
**Rationale**: Prevents weak human-chosen secrets and guarantees the secret↔IP pairing is fixed
for the life of the key.
**Examples**:
- Editing a key only changes status, the two service flags, and notes.
- To re-bind a key to a new IP, the admin deletes it and adds a new one (a new secret is issued).

### BS-432: Ticket Overdue Qualification
**Rule**: During the overdue sweep, an open, not-already-overdue ticket becomes overdue per the
reopened-aware grace qualification math owned by **FS-032.11** (creation-vs-reopen grace window
and explicit-due-date check). At most 50 tickets are aged per invocation, oldest first, and each
newly overdue ticket logs the activity "Ticket Marked Overdue".
**Rationale**: SLA breach detection without a heavyweight scan; the 50-ticket cap bounds
per-invocation cost so cron stays fast.

### BS-433: Full Cron Cycle Is Upgrade-Gated and Ordered
**Rule**: A full cron cycle runs its four jobs only when the system is initialized and no upgrade
is pending, in the fixed order mail-fetch → ticket-monitor → purge-logs → clean-orphaned-files.
**Rationale**: Running maintenance against a schema mid-migration risks corruption; the fixed
order ensures fetched mail is threaded before downstream sweeps and that cleanup runs last.

### BS-434: Mail-Fetch Is Cron Job #1
**Rule**: Mail-fetch is the first job of the full cron cycle. Whether fetching runs at all is gated
by the global *email polling* setting; the per-account cadence, error-backoff, and time-box numbers
are owned by **FS-041** (.3 / BS-041.5/6/15).
**Rationale**: Fetched mail must be threaded before the downstream sweeps run; the execution
mechanics live with the inbound-pipeline spec to avoid restating the same numbers in two homes.

### BS-435: Autocron Is a Throttled, Session-Scoped Fallback
**Rule**: Autocron performs cron work at most once per 3 minutes per staff session, always runs
the ticket-monitor job, runs mail-fetch only if autocron is enabled, never runs log-purge or
orphaned-file cleanup, requires no pending upgrade, and clears the acting-staff identity before
running so cron-produced side effects are not credited to the triggering user.
**Rationale**: Lets installations without a real system cron still age tickets, without spawning
cron on every page load and without misattributing automated actions to a human.

### BS-436: Stateless API — No Sessions
**Rule**: API requests disable session handling entirely (session save handler no-op'd,
`DISABLE_SESSION` set); the API is authenticated solely per-request by API key.
**Rationale**: API clients are machines; persisting a session row per call would needlessly grow
the session table and is meaningless for stateless calls.

### BS-437: Soft Attachment Validation
**Rule**: Attachment-level problems (disallowed type, bad base64, oversize) are recorded against
the individual attachment and do not fail the ticket-create request; the ticket is still created,
minus the offending file(s). If API attachments are globally disabled, all attachments are
dropped silently.
**Rationale**: A single bad file should not cost the customer their ticket; the message content is
preserved.

### BS-439: Email-Format Submissions Thread Before Creating
**Rule**: A ticket-create request in the **email** format flows through the shared
fixup → reply-detection → threading pipeline before a new ticket is created. The payload fixup
defaults are owned by **FS-041.5.3** and the reply-detection / threading precedence by **FS-041.6**;
this spec owns only the HTTP wire framing (format dispatch, email field allow-list, single 201
response per FS-043.14).
**Rationale**: Inbound email is conversational — replies to existing tickets must continue the same
thread, not spawn duplicate tickets. The same logic is reused by the local mail pipe (FS-041) so
piped and API-posted email behave identically, which is exactly why the threading rules live in
FS-041 and not here.

### BS-440: Local Mail Pipe Reports via MTA Exit Codes, Not HTTP
**Rule**: The local email-pipe controller reuses the ticket-create / reply-detection pipeline but
overrides the responder to emit BSD-sendmail process exit codes instead of HTTP statuses, and
requires no API key. The HTTP→exit-code mapping table is owned by **FS-041 BS-041.2**; this spec
records only that the pipe controller specializes the API controller to apply it.
**Rationale**: A mail-transfer agent invoking the pipe interprets exit codes to decide whether to
bounce or retry delivery; HTTP statuses are meaningless in that context.

### BS-438: Only Ticket-Create and Cron Are Exposed Over HTTP API
**Rule**: The mounted API route table exposes exactly two capabilities — POST ticket creation (in
xml/json/email formats) and POST remote cron — and nothing else; no read, update, or delete of any
resource is available over the API.
**Rationale**: osTicket 1.7's API is intentionally minimal (creation only); the dispatcher refuses
any unmatched path with HTTP 400.

## Data Requirements

The API & cron subsystem reads/writes the following (canonical schema → FS-091):

- **API key** (`ost_api_key`): `id`, `apikey` (32-char uppercase hex secret), `ipaddr` (bound
  source IP), `isactive` (flag), `can_create_tickets` (flag), `can_exec_cron` (flag), `notes`
  (text), `created`, `updated`.
- **Ticket-create payload** (transient, not persisted as-is): accepted top-level fields `alert`,
  `autorespond`, `source` (default `API`), `topicId`, `name`, `email`, `subject`, `phone`,
  `phone_ext`, `attachments[]`, `message`, `ip`, `priorityId`; plus, for the email format,
  `header`, `mid`, `emailId`, `ticketId`, `reply-to`, `reply-to-name`, `in-reply-to`,
  `references`. Each attachment: `name`, `type` (MIME, default `text/plain`), `data`, `encoding`
  (`base64` optional). Parsed payload feeds ticket creation (→ FS-011) and yields the new external
  ticket ID on success.
- **Mail account** (`ost_email` — read for cadence; → FS-040/FS-041): `mail_active`,
  `mail_fetchfreq` (minutes), `mail_lastfetch`, `mail_errors`, `mail_lasterror`, `max_fetch`,
  `archive_folder`.
- **Cron-touched data**: tickets (overdue flag, SLA grace period, due date, reopen time → FS-021),
  ticket locks (expiry → FS-021), system log entries (`ost_syslog`, age-based purge → FS-033),
  file records + chunks (orphan detection → FS-022).
- **Config keys consumed**: `enable_auto_cron` (autocron mail-fetch gate), `enable_mail_polling`
  (global mail-fetch gate), `log_graceperiod` (months of system-log retention), the
  email/API-attachment enable flag, and max file size. (Canonical config → FS-032/FS-091.)
- **Session value** (autocron only): `lastcroncall` (last autocron-run epoch, per staff session).

## User Flows / Interactions

### Flow A: Administrator registers an API key
1. Admin opens Manage → API Keys → *Add New API Key*.
2. Admin enters the client's source IP, chooses Active, ticks the needed service(s) (Can Create
   Tickets and/or Can Execute Cron), optionally adds notes, and saves.
3. The system validates the IP, auto-generates the 32-char secret, stores the record, and shows
   *"API key added successfully"*.
4. Admin copies the generated key value from the list/edit view and provides it (plus the IP
   binding requirement) to the API consumer.

### Flow B: External client creates a ticket via JSON
1. Client POSTs to `/api/tickets.json` with header `X-API-Key: <secret>` and a JSON body.
2. The dispatcher matches the POST + path, resolves `format=json`, and invokes ticket-create.
3. The controller authenticates the key (secret + active + source-IP + `can_create_tickets`).
4. The JSON parser normalizes the body (phone-ext split, attachments from data-URLs, etc.).
5. The controller validates field keys against the allow-list and validates attachments (soft).
6. A ticket is created; the response is **201** with the new external ticket number as the body.
7. On any failure, the response is the relevant 4xx/5xx with a plain error message, and the
   failure is logged with the key appended.

### Flow C: Scheduled maintenance via system cron (recommended)
1. The host OS scheduler runs the local CLI cron entry point on a timer (e.g. every few minutes).
2. The entry point confirms CLI invocation, then runs the full cron cycle (mail-fetch →
   ticket-monitor → purge-logs → clean-orphans), upgrade-gated.
3. Success exits silently (0); errors print and exit 1.

   *(Alternative: an external host POSTs to `/api/tasks/cron` with a `can_exec_cron` key — the
   reference `rcron.php` client — yielding 200 "Completed".)*

### Flow D: Autocron fallback (no system cron configured)
1. A staff member loads any control-panel page; the footer's 1×1 GIF requests `autocron.php`.
2. The handler returns the GIF immediately and continues in the background.
3. If ≥3 minutes have passed since this session's last autocron run and no upgrade is pending, it
   clears the acting-staff identity, runs the ticket-monitor job, and — if autocron is enabled —
   runs mail-fetch, recording `lastcroncall`.

## Edge Cases

- **EC-430 — No API key header**: Request to a protected endpoint without `X-API-Key` → 401
  "Valid API key required".
- **EC-431 — Right secret, wrong IP**: Correct secret but source IP ≠ bound IP → 401 "API key not
  found/active or source IP not authorized".
- **EC-432 — Correct key, missing permission**: Authenticated key lacking the endpoint's flag →
  401 "API key not authorized" (create vs. cron flags are independent).
- **EC-433 — Unknown URL/format**: POST to an unmounted path → 400 "URL not supported"; a
  ticket path with an unrecognized extension → 415 "Unsupported data format".
- **EC-434 — Unexpected field**: Body contains a key outside the format's allow-list → 400
  "<path>: Unexpected data received".
- **EC-435 — Malformed body**: Unparseable XML/JSON/email → 400 with the parser error; ticket
  endpoint reports 400 "Unexpected or invalid data received" on structure-validation failure.
- **EC-436 — XML capability absent**: `tickets.xml` request when XML parsing is unavailable → 501
  "XML extension not supported".
- **EC-437 — Bad base64 attachment**: Attachment declared base64 but undecodable → per-attachment
  error recorded; the ticket is still created without that file (soft fail).
- **EC-438 — Oversize / disallowed attachment**: Recorded as a per-attachment error; ticket still
  created. If API attachments are globally disabled, all attachments are silently dropped.
- **EC-439 — Ticket creation denied by filter**: If ticket creation returns the denied (403)
  condition (e.g. an inbound filter rejects it → FS-042), the API responds 403 "Ticket denied";
  other validation errors → 400 with the flattened error list; unknown failure → 500.
- **EC-440 — Local cron invoked over HTTP**: `cron.php` reached via the web rather than CLI →
  prints "cron.php only supports local cron calls - use http -> api/tasks/cron" and stops.
- **EC-441 — Cron during pending upgrade**: A full cron cycle (and autocron) does nothing while a
  schema upgrade is pending, preventing maintenance against a half-migrated schema.
- **EC-442 — Mail polling disabled / IMAP missing**: Mail-fetch returns immediately if global
  polling is off; if IMAP is unavailable it logs a warning and skips.
- **EC-443 — Mail server unreachable**: A persistently failing account backs off and alerts the
  admin, and the fetch loop yields before cron overruns its execution window. The backoff/time-box
  thresholds are owned by FS-041 (.3 / BS-041.5/6/15); cron only invokes the fetch job (FS-043.8).
- **EC-444 — Autocron rapid reloads**: Multiple staff page loads within 3 minutes of the last
  autocron run are no-ops (session throttle), so cron is not spawned on every page view.
- **EC-445 — No log grace period**: If `log_graceperiod` is unset or non-numeric, the log purge is
  a no-op (logs are retained indefinitely).
- **EC-446 — Method emulation**: A `_method=POST` GET argument lets a client that cannot issue a
  raw POST still reach a POST-only route.
- **EC-447 — Email-format reply vs. new ticket**: A `tickets.email` request whose `ticketId`
  resolves to an existing ticket, or whose headers match an existing thread, is **threaded as a
  reply** onto that ticket rather than creating a new one; only when neither matches is a new ticket
  created. All three outcomes return 201 with a ticket identifier (FS-043.14).
- **EC-448 — Unreadable request stream**: If the raw input/stdin stream cannot be opened, the
  endpoint returns 400 "Unable to read request body" before parsing.
- **EC-449 — Local email-pipe outcomes map to MTA exit codes**: The local pipe path never emits
  HTTP; success exits 0, permission/format/temporary failures map to the BSD-sendmail exit codes in
  FS-043.15 so the mail-transfer agent can decide to bounce or retry.

## Known Limitations

- **KL-430 — Doc/code divergence on per-key entitlement**: The bundled API doc (`setup/doc/api.md`)
  states *"no special configuration is required... All API keys are valid for the HTTP API,"* but
  the code enforces per-key `can_create_tickets` / `can_exec_cron` flags. A key without
  `can_create_tickets` is rejected with 401 despite being "valid." The **code is authoritative**.
- **KL-431 — IP binding is exact-match, single IP**: Each key binds to exactly one source IP; there
  is no CIDR range, no multi-IP binding, and no per-key IP allow-list. Clients behind dynamic IPs
  or load-balanced egress require a key per IP (or a stable proxy IP). IP spoofing via a forged
  `X-Forwarded-For` is possible if the deployment trusts that header without a vetted proxy.
- **KL-432 — Secret is a 32-char MD5 of low-entropy inputs**: The key is `MD5(time + ip +
  MD5(rand16))`; while not directly user-guessable, MD5 and a partly time-derived seed are weak by
  modern standards. There is no key rotation, expiry, or rate limiting on the key itself.
- **KL-433 — Cron is not DB-scheduled**: Source comments note the intent to make cron DB-based; in
  1.7 the job set is hard-coded in `class.cron.php` with no per-job schedule, no last-run
  persistence, and no admin-visible cron status. Cadence is entirely external (the OS scheduler or
  autocron's 3-minute session throttle).
- **KL-434 — Overdue sweep ages only 50 tickets/run with no escalation**: Large backlogs may take
  several cron cycles to fully flag overdue; the code's "trigger escalation on already-overdue
  tickets" branch is an unimplemented TODO (no repeat-escalation logic).
- **KL-435 — Autocron coupling to page loads**: Autocron only fires while staff are actively
  browsing the control panel and is throttled per session; an idle install (no staff online) does
  no autocron maintenance at all, so a real system cron is still required for reliable, unattended
  operation. Autocron also never runs log-purge or orphaned-file cleanup.
- **KL-436 — No read/update/delete API**: Only ticket creation and cron are exposed; there is no
  API to query, update, close, or delete tickets, nor to manage any other resource, in 1.7.
- **KL-437 — Activity-log purge is a TODO**: `purgeLogs` purges only the system log; the
  activity-log purge is an unimplemented TODO comment.
- **KL-438 — JSON attachment charset hint is effectively ignored**: For a `data:` attachment URL
  carrying a `charset=` hint, the JSON parser computes a UTF-8-converted copy of the contents but
  builds the attachment record from the **pre-conversion** value; the converted bytes are written to
  a local variable that is never stored back. In practice a non-UTF-8 charset hint on a JSON
  attachment does **not** re-encode the stored data, despite the inline comment claiming it does.
- **KL-439 — Local cron entry double-includes the bootstrap**: The local CLI cron entry script
  includes the API bootstrap (`api.inc.php`) and changes directory **twice** before invoking the
  controller. This is a harmless redundancy (the bootstrap is include-guarded) but is dead/duplicate
  code, not an intentional two-stage init.
- **KL-440 — Dispatcher is method-capable but only POST is wired**: The router exposes generic
  GET / POST / DELETE matcher helpers, so the *creation-only* nature of the API is purely a function
  of which routes are mounted, not an architectural limit. A future read/update API would slot into
  the existing dispatcher without framework changes.

## Future Considerations

- A DB-scheduled cron subsystem with per-job cadence, last-run tracking, and admin-visible status
  (as the source TODOs anticipate) would replace the hard-coded job list and the autocron crutch.
- A richer API (key scopes/CIDR binding, key rotation/expiry, rate limiting, and read/update
  resource endpoints) would address KL-430 through KL-436.
- Replacing the MD5-derived secret with a CSPRNG-generated token and supporting multiple
  bound IPs/ranges per key would harden authentication.
